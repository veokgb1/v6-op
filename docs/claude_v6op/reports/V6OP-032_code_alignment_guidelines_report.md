# V6OP-032 代码对齐与问题解决规范

日期：2026-05-06

范围：面向 Codex、Claude 和后续开发者，统一 V6OP 的技术栈、代码风格、模块边界、异常处理、日志、报告、测试和问题处理顺序。目标是减少“修一个坏一个”的循环。

## 1. 总原则

V6OP 的开发原则：

1. 用户动线优先：代码服务于“选来源、选技能、调参数、启动、看结果”。
2. 真实数据优先：不得用 fixture 或旧报告冒充当前真实运行。
3. 证据优先：任何结论必须能追到 run_id、query、参数、数据日期、日志或测试。
4. 小步收敛：简单问题先解决，复杂问题先设计再实现。
5. 不碰 V5 原目录：V5 只读参考，不直接修改。
6. 不泄露密钥：`.env`、API key、cookie、token 不进报告、不进日志、不进测试产物。

## 2. 技术栈口径

| 项目 | 当前口径 |
|---|---|
| 后端语言 | Python |
| 前端 | 原生 HTML/CSS/JS 单页应用 |
| 服务 | `scripts/v6op_server.py` |
| Python 环境 | 项目 `.venv`，不要一会儿系统 Python 一会儿 venv |

| 当前运行产物 | `output/current` |
| 历史运行产物 | `output/runs/<run_id>` |

### Python 环境规范

统一使用：

```powershell
F:\v.6\v6-op\.venv\Scripts\python.exe
```

不要混用：

- 系统 Python
- Windows Store Python
- 其他项目 venv

如果 `.venv` 被误删，应按 `requirements.txt` 重建，不把 `.venv` 当作长期业务资产。

## 4. 命名规范

### 用户可见命名

用户界面必须使用中文可懂词：

| 内部词 | 用户词 |
|---|---|
| scope | 来源股票池 / 来源总数 |
| cache | 本地保存；必须注明是哪一种 |
| prefetch | 本轮补 K线 |
| stale | 旧 K线 |
| producer | 技能 |
| final_hits | 最终命中 |
| failed | 取数失败 / 未分析，不得混入命中 |

### 三层数据标记

统一使用：

- `★ 问财来源快照`：本轮问财、全 A、手动拿到的股票池，下一轮可能覆盖。
- `★★ K线数据库`：已保存到本机的日 K 线，电脑重启后仍可复用。
- `★★★ 技能结果库`：同股票池、同参数、同日期算出的技能结果，可以复用。

### 档位命名

不要笼统叫 `PRO 5000`。

建议：

- 问财模式：`问财最多 5000`
- 全 A 模式：`本地A股最多 5000`

## 5. 模块契约

### 5.1 source_resolver 契约

来源层只负责生成股票池，输出必须包含：

- `source_type`
- `scope_codes`
- `scope_count`
- `status`
- `limit`
- `query`，如果是问财
- `api_called`
- `env_key_present` 或等价安全字段
- 错误原因

禁止：

- 来源层不要直接跑技能。
- 板块扫描不要变成新的主 source_type。板块扫描是 Phase A 辅助，结果注入 Phase B 问财语句。

### 5.2 fetch_planner 契约

K线准备层必须回答：

- 本轮来源池有多少只。
- 本地 K线可用多少只。
- 缺 K线多少只。
- 旧 K线多少只。
- 取数失败多少只。
- 最新 K线日期是什么。
- 是否允许继续分析。

注意：

- “有文件”不等于“数据新鲜”。
- “本地K线可计算”不等于“今天行情已经更新”。
- 必须使用本轮技能需要的最大回看天数，不允许默认 365 偷跑。

### 5.3 producer 契约

每个 producer 必须统一：

- 输入：`codes`、参数、K线缓存路径。
- 输出：`hit_codes`、`miss_codes`、`evidence`、`params_used`、`elapsed_seconds`、`warnings`。
- producer 阶段默认只读本地 K线，不访问问财，不补网络。

禁止：

- 不得硬编码回看天数覆盖 UI 参数。
- 不得把失败股票混入未命中。
- 不得静默吞掉关键错误。

### 5.4 execution_engine 契约

执行层负责：

- 生成 run_id。
- 解析来源。
- 准备 K线。
- 执行技能。
- 合并路径结果。
- 写当前结果和归档结果。
- 响应 abort。

注意：

- sequential、parallel_and、simple_hybrid 的最终结果必须和报告表达式一致。
- 长期目标是统一成 graph execution；短期可以保留三路径分支，但必须测试覆盖。

### 5.5 run_report 契约

报告必须记录：

- run_id
- 生成时间，统一 CST
- 来源类型、query、limit、实际返回数
- 数据状态、最新 K线日期、旧 K线警告
- 所有技能参数
- 路径类型
- 命中列表
- 失败/未分析列表
- warnings
- 报告不能泄露 key

## 6. 异常处理规范

### 来源异常

必须区分：

| 情况 | 状态 |
|---|---|
| 问财真的没有符合股票 | `empty_result` |
| 问财接口失败 | `api_error` |
| key/session/权限失败 | `auth_error` |
| raw schema 无法提取代码 | `parse_error` |
| 用户没输入 query | `invalid_request` |

不能全部写成“问财无结果”。

### K线异常

必须区分：

| 情况 | 处理 |
|---|---|
| 本地已有且日期可接受 | 继续 |
| 本地已有但旧 | 继续或警告，按策略 |
| 缺 K线 | 触发补 K线 |
| 补取失败 | 进入 failed，不混入命中 |
| 写缓存失败 | 必须记录 warning / failed |

### 技能异常

单只股票异常：

- 可以记录为该股票未分析或失败。
- 不应让整轮崩掉，除非是全局配置错误。

全局异常：

- 必须写 `execution_result.json` 和 `run_report.json`。
- 页面要显示中止/失败状态，不能保留上一轮成功结果冒充当前结果。

## 7. 日志规范

运行日志必须能回答四件事：

1. 现在在哪一步。
2. 本步输入多少只。
3. 本步输出多少只。
4. 为什么失败或跳过。

建议日志结构：

```text
步骤 1/8：解析股票来源
问财 query=...
问财返回 actual_count=...

步骤 2/8：检查本地K线
来源总数=... 本地可用=... 缺K线=... 旧K线=...

步骤 5/8：运行技能
运行 K线形态 输入=... 命中=... 未中=... 失败=...
```

大规模取数时，需要恢复类似 V5 的瀑布感，但不要刷无意义噪音。每批、每源、每个失败原因都要能追。

## 8. 报告规范

### Markdown 报告

面向用户，必须中文可读。

必须包含：

- 本轮来源
- 本轮参数
- 数据新鲜度
- 命中结果
- 每只命中原因
- 未分析/失败原因
- 风险提示

### JSON 报告

面向前端和自动测试。

必须结构稳定，字段新增可以，字段删除要谨慎。

### 时间规范

统一使用中国时间：

- 显示：`YYYY-MM-DD HH:mm:ss CST`
- 机器字段：ISO +08:00

不要再出现伦敦时间、UTC 时间和本地 naive time 混写。

## 9. 测试规范

### 每次修后必须考虑的测试

| 改动类型 | 最少测试 |
|---|---|
| 前端 JS | `node --check web/app.js` |
| 后端 Python | 相关 pytest |
| source_resolver | manual/all_a/wencai mock 测试 |
| wencai_source | query、limit、空结果、接口失败、解析失败 |
| fetch_planner | 缺 K线、旧 K线、失败率、days |
| producer | 参数变化影响结果 |
| execution_engine | 三路径最终命中、aborted、failed 不混命中 |
| run_report | 字段完整、时间 CST、密钥不泄露 |

### 禁止

- 不得用 HTTP smoke 冒充真实浏览器验收。
- 不得用旧 output/current 结果冒充新运行结果。
- 不得只测 happy path。

## 10. 问题分级与处理顺序

### P0：立刻阻断

- 密钥泄露。
- 当前 run 显示上一轮结果。
- 问财空结果被当作成功。
- failed 股票混入命中。
- 参数显示和实际计算不一致。

### P1：优先修复

- `PRO 5000` 语义误导。
- K线日期过旧但 UI 显示“够用”。
- 取数失败被静默吞掉。
- 中止运行不能可靠停止。
- 报告缺少来源 query 和实际返回证据。

### P2：计划修复

- 三路径统一成 graph execution。
- V5 报告格式进一步对齐。
- 历史报告选择器。
- 清缓存、清日志、断点续跑。
- 灰色技能逐个接通。

### P3：后续增强

- 打分制。
- 抗压排名。
- AI 解释增强。
- 更多数据源。

## 11. 先易后难执行法

### 可单人直接做

- 文案和帮助提示。
- 报告补字段。
- 时间统一。
- 小范围参数 bug。
- 单个 producer 的测试补齐。

### 需要先写设计

- 问财真实授权机制。
- full scan 三源降级。
- abort worker 强中止。
- 清缓存/清日志/历史报告/续跑。
- graph execution 替换三路径分支。

### 需要多人审

- 打分制和并行积分。
- 抗压/防回撤模型。
- 第二阶段灰色技能批量接入。
- 交易策略解释和排序模型。

## 13. 当前优先对齐清单

基于 V6OP-030，下一批建议顺序：

1. 问财来源真实性：key/session/query/raw schema/分页/实际返回数。
2. `PRO 5000` 和全 A / 问财档位命名拆开。
3. K线回看天数端到端一致，修复缠论硬编码 365。
4. K线数据库“可计算”和“最新日期”分开显示。
5. full scan 三源降级和 worker 中止设计。
6. 报告补全 query、limit、actual_count、api_called、data_time_max。
7. output/current run_id 对齐，避免旧文件误导。
8. 再讨论续跑、清缓存、历史报告。

## 14. 本文档的使用方式

以后遇到问题时，先判断它属于：

- 来源层
- K线层
- 技能层
- 路径组合层
- 报告层
- 前端解释层
- 运行管理层

不要直接跳到“改按钮”或“调参数”。先定位层，再看契约，再决定是快速修、写设计，还是多人审。

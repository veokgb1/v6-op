## 1. 用户视角的真实痛点

请从用户视角先复述当前情况，不要只从代码视角说“哪个函数错了”。

用户现在的痛点是：

1. 第一阶段看起来签收过，但真实使用时仍然会出现问财返回 0、PRO 5000 含义不清、K线库是否真实可用不清、路径筛选为什么为 0 不清。
2. 复杂筛选链路很难理解：来源池、问财、K线数据库、技能结果库、顺序漏斗、并行交集、排雷负向过滤混在一起，用户不知道问题出在哪一层。
3. 用户不希望以后变成“出现一个问题，就在那一处补一刀”。需要一个中立、模块化、可复用的解释模板。以后每个问题都先按模板定位，再决定修哪里。
4. 当前页面越来越重。`web/app.js` 虽然实际约 1549 行、72KB，但它已经混入来源、收藏、板块、P1-P6、帮助说明、技能参数、运行状态、报告、缓存说明、压力测试说明等内容。继续往首页塞管理功能，会让页面和维护心智失控。
5. 章程要求“单页操盘体验”，但这不等于“所有管理功能和所有 JS 都塞在首页”。用户要求把管理类应用分流出来：主页面保留每日操盘动线，收藏、预设、报告历史、缓存管理、帮助说明、技能资产等进入管理区或独立模块。

## 4. 本轮第三交付：页面分流设计

请重点分析并给出页面分流方案。

核心判断：

> 单页操盘体验不等于单文件大杂烩。主页面应该轻，管理功能应该分流。

请给出至少两种方案：

### 方案 A：保留单入口，前端模块拆分

目标：

- 用户仍打开一个操盘台。
- 但 JS 拆成多个模块，减少 `web/app.js` 继续膨胀。

可能拆分：

```text
web/app.js                  主入口/事件编排
web/state.js                状态与本地存储
web/api.js                  API 请求
web/render.js               主渲染
web/source_panel.js         来源/问财/板块
web/skills_panel.js         技能参数
web/run_panel.js            启动/中止/日志
web/report_panel.js         报告与命中展示
web/help_text.js            小 i 帮助说明
web/presets_favorites.js    P1-P6/收藏/档位
```

### 方案 B：主操盘台 + 管理中心

目标：

- 每日操盘主页面只保留最常用动作。
- 管理类功能放到管理中心，避免首页越塞越重。

建议分流：

主操盘台保留：

- 股票来源
- 问财语句/全A/手动
- 常用预设入口
- live 技能勾选和关键参数
- 三种路径
- 启动/中止
- 日志/数据状态/命中结果

管理中心承接：

- P1-P6 预设维护
- 问财收藏
- 板块收藏
- 历史报告选择
- 清缓存/清日志
- 帮助说明全文
- 技能资产列表
- 灰色技能说明
- 压力测试说明
- 后续打分/抗压模型配置

请说明两种方案的风险、工期、测试方式，并给出你推荐的第一刀。

## 一、第一部分判断：是否属于第二阶段初期主范围

第一部分的六项内容都应纳入第二阶段，但需要区分"初期必做"和"初期定义、中期落地"两个节奏。

### 1. 查询为 0 后的分层解释

**判断：必须初期做，而且应该是第一批。**

这不是一个锦上添花的展示功能。当结果为 0 时，用户现在完全不知道是来源返回了空、还是 K 线不足、还是技能过严、还是并行交集太严。这四种情况对应完全不同的下一步操作，但系统把它们全部压缩成同一个空结果。这是第一阶段里"结果不可信"最直接的体现。

五层解释（来源层、数据层、技能层、路径层、报告层）的完整契约应该在第二阶段初期就定义清楚，实现则可以分两步：先把最关键的两层（来源层、技能层）做到可见，再把其余三层补齐。不能因为五层一起做而推迟。

### 2. PRO 5000 语义拆分

**判断：必须初期做，而且是低成本高收益项。**

"问财最多取 5000"和"全A最多截 5000"是完全不同的两件事，混用一个标签是用户混乱的直接来源。问财 0 / 45 / 5000 截断各有不同含义，目前系统对用户完全不解释。这个问题不是代码结构问题，是语义定义和标签问题，改动量不大，但解决的困惑量很大。必须初期做。

### 3. Data Provider Adapter + Data Provenance

**判断：初期定义架构，中期在运行结果里落地。**

这个方向是对的，但实施顺序很重要。第二阶段初期应该先定义清楚：baostock / akshare / yfinance / 问财 / 手动导入等各来源的统一接口规范是什么，数据血缘的字段是什么（来源、日期、是否降级、是否用旧缓存）。这个定义完成后，中期再把它"说清楚"的地方落到运行报告和状态区，而不是新建一个"数据管理页面"。

最关键的警戒线：Data Provenance 的展示位置必须是运行结果的一个折叠区，不能是独立的可浏览页面。一旦变成独立页面，就偏离了单页操盘动线。

### 4. 问财作为 Bridge Capability

**判断：初期定义概念，中期实现第二种角色。**

问财当前只是"来源层的股票池生成器"。它的第二种角色（对已有股票池做外部验证/标签/概念确认）在概念上已经清晰，但它的实现涉及引擎层的一次额外网络查询，时序设计也需要明确。初期的任务是把两种角色（来源模式 vs 验证模式）明确区分定义，并决定它的触发条件。实现可以在第二阶段中后期。

这个概念的关键约束：Bridge Capability 必须是主操盘台里一个参数选项，不能变成一个独立的"问财查询管理页面"。

### 5. 主操盘台与管理中心分流

**判断：正确方向，第二阶段中期落地，初期先定义清楚边界。**

这个方向和原始大纲不矛盾，反而是对原始大纲的正确解读。大纲说"单页操盘体验"，意思是"主操盘动线不需要跳页"，不是"所有功能必须在同一个屏幕视野里"。当前页面把操盘必要内容和管理/诊断内容混在一起，让用户在操盘时要处理太多噪音。

分流的边界必须在初期就定义好（见第三节），落地可以在中期。不能等到管理中心的功能全部设计完才开始实施，否则会陷入"先设计一个完整管理系统再分流"的陷阱。

### 6. 第二阶段推进顺序

**判断：透明度先于架构重构，架构重构先于页面分流，都先于执行引擎改造。**

这个顺序是正确的，理由是：透明度是信任的基础，没有透明度，用户无法判断后续的任何架构改动是否有效；架构定义是实施的基础，没有明确的 Provider Adapter、Provenance、Bridge 等概念边界，后续实施容易走偏；页面分流是用户体验的改善，依赖前两步对内容的明确分类；执行引擎统一是最大的架构债，放在最后是因为它的改动范围最大、风险最高，应该等其他层稳定后再动。

## 二、第二部分判断：是否纳入第二阶段，会不会导致膨胀

### 1. 分层问题定位解释器的完整契约

**判断：纳入，作为设计规格文档，不是立即可执行的施工单。**

把五层解释（来源、数据、技能、路径、报告）的输入/输出/失败原因/用户下一步建议完整定义出来，是第二阶段初期的必要工作。它的价值不是立即生成代码，而是让实施时有一个明确的契约，避免"做到一半发现某层的定义和其他层不一致"。

建议作为第二阶段的一份正式文档（不是代码），在动手前完成，供所有开发轮次参考。

### 2. Data Provenance 数据血缘层

**判断：纳入，但只作为"运行结果的一部分"，不作为独立的可浏览数据层。**

数据血缘的字段定义（股票池来源、行情来源、是否新拉、是否失败、旧数据日期、可信度标注）应该在第二阶段初期定义，但"展示"是在运行报告里，不是在一个独立的数据管理界面。关键区别：用户看完这轮运行后，能在报告里看到"本轮数据：baostock 342 只 / akshare 兜底 12 只 / 失败 3 只 / 最旧数据 2026-04-15"，这是透明度。但如果做成"点击查看数据血缘"跳转到一个可以按来源浏览所有历史数据的页面，那就是博物馆。

### 3. Bridge Capability 正式概念

**判断：纳入，作为设计规格定义，同时决定 constrained mode 和 intersect mode 的触发逻辑。**

Constrained mode（问财查询约束在已有股票池内）和 intersect mode（问财查询结果与已有结果取交集）的区别很重要。这两种模式的行为不同，用户看到的结果差异可能很大，需要在 UI 上能区分选择。

纳入第二阶段的方式：初期先把两种模式的语义规格写清楚，中期再实现第二种角色的实际调用逻辑。

### 4. 问财二次验证的未来使用场景

**判断：纳入为"第二阶段中后期的能力扩展"，不是初期。**

"先跑缠论/K线/SMC/排雷，对剩余股票再做问财概念/公告/资金/行业验证"这个场景是有价值的，但它的实现前提是：
- 问财授权已经验证稳定；
- Bridge Capability 的调用接口已经定义好；
- 执行路径的时序已经有足够灵活性。

这三个前提都需要先在第二阶段中期完成。因此二次验证本身放在第二阶段后期更合适。提前规划，延迟实施。

### 5. 第二阶段四步推进顺序

**判断：与第一部分判断一致，接受并固化为本轮对齐结论。**

解释透明度 → 架构定义 → 页面分流 → 决定是否改执行引擎。
这个顺序既有逻辑依赖关系（透明度是基础），也有风险控制考虑（执行引擎改造放最后）。

### 6. 第二阶段定位

**判断：完全接受，作为第二阶段的首要原则写入纲要。**

"不是新增功能优先，而是建立透明机制和分类机制；先让用户知道结果为什么这样，再扩展技能、打分、抗压模型。"这句话和 012 的宗旨是同一件事的两种表达，可以合并为一句：

> **第二阶段的第一优先级是：让用户在操盘时，能看到自己在相信什么。扩展技能和新能力在透明度建立之后才有意义。**

### 会不会导致膨胀？

整体来说，第二部分的内容不会导致第二阶段膨胀，但有一个条件：它们必须以"设计规格"的方式纳入，而不是立即变成独立的新功能模块。膨胀的触发点通常不是"想法太多"，而是"每个想法都要有自己的独立 UI 入口"。只要严格遵守"所有诊断信息展示在运行结果内、所有管理功能集中在管理中心、主操盘台只保留操盘动线"，第二部分的内容不会让系统膨胀。

## 三、偏离"单页操盘动线"的风险判断

### 哪些内容有博物馆/卡片化风险

| 内容 | 风险描述 | 风险等级 |
|------|----------|----------|
| Data Provenance | 如果做成可浏览的数据来源历史页面 | 高 |
| 管理中心 | 如果承接了分析能力或成为第二个操盘台 | 高 |
| Bridge Capability | 如果为"问财验证模式"单独做一套操盘流程 | 中 |
| 历史报告 | 如果每条报告变成可交互的"卡片"，支持对比/收藏/标注 | 中 |
| 分层解释器 | 如果解释层做成独立的"诊断中心"页面 | 中 |
| 来源诊断字段 | 如果做成"来源管理"页面 | 低（展示在结果内则无风险） |
| PRO 5000 语义 | 无独立页面风险，只是标签和提示文案 | 无 |

### 如何做才不偏离

**核心原则**：不是"这些内容不能做"，而是"这些内容的展示位置决定了它是工具还是博物馆"。

- **所有诊断和血缘信息 → 展示在当前运行结果内**（折叠区或侧栏），不开独立页面。
- **所有管理和历史功能 → 集中在一个管理中心入口**，管理中心只做管理，不做分析。
- **所有 Bridge/Provenance 能力 → 以参数选项或运行时标注的方式存在**，不是新的主操作路径。
- **主操盘台保留的内容只有七项**：来源选择、技能选择、参数调节、路径选择、启动、状态/日志、结果（含本轮解释）。

### 主操盘台保留边界（只有这些）

1. 股票来源选择（问财 / 全A / 手动 / 板块）
2. 技能开关和参数
3. 执行路径选择
4. 启动按钮 + 进度状态
5. 命中结果列表
6. 本轮全局解释（为什么是这个结果，分层展示，在结果区内）
7. PRO 5000 档位和来源诊断（内联在来源区，不是独立区）

### 管理中心只承接这些

- 历史运行记录（简单时间序列列表，点击可恢复参数）
- 分层缓存清理（来源快照 / K线数据库 / 技能结果库三层分开）
- 系统设置（问财 key、默认参数、取数模式）
- 帮助文档和技能资产说明（只读参考）
- 问财授权状态检查（不是分析能力，是配置状态确认）

### 只作为折叠/二级入口，不进入主操作路径

- 完整数据血缘报告（结果区折叠展开）
- 详细执行路径追踪（结果区折叠展开）
- 每个技能的参数详情（技能卡折叠展开）
- 历史对比（管理中心的二级功能，不在主操盘台）

## 四、第二阶段大目标（共 8 个）

以下 8 个目标按建议排序排列，每个目标是一个能力块，不是修单点 bug 的列表。每个目标包含若干第一阶段补丁，但核心是建立新能力。

---

### G1：参数-数据-缓存全链路一致化

**解决什么用户问题**：用户改了技能参数（如 days=730），但结果没有变化，不知道参数是否真的生效。这是"结果不可信"最根本的来源之一。

**包含哪些能力**：
- czsc days 参数传递修复（当前硬编码 365）
- fetch_planner lookback_days 接入 execution_engine 的实际调用
- mask_cache 指纹与实际使用的 days 保持一致（避免指纹说是新值但 K 线仍取旧长度）
- 验证 smc/kline days 的传递链路是否已完整（参考代码显示已传，需确认全链路）
- K线"够用"判断条件改为基于用户设置的 days，不是默认 365d.pkl

**是否属于第二阶段初期**：是，第一批。

**是否有偏离操盘动线风险**：无（纯后端链路修复）。

**如何避免偏离**：N/A。

---

### G2：全局解释层与分层归零诊断

**解决什么用户问题**：结果为 0 时用户无从判断是哪一层造成的，无法决定下一步应该调什么。部分命中时（如 3 只），用户也不知道为什么只剩 3 只。

**包含哪些能力**：
- 正式定义五层解释契约（来源层、数据层、技能层、路径层、报告层），每层输出：输入是什么、产出是什么、本轮有没有失败、失败原因是什么、建议用户做什么
- 来源层：本轮问财返回多少只、实际取到多少只、为什么
- 数据层：K 线覆盖多少只、多少只不足、哪些来自旧缓存
- 技能层：每个技能命中多少只、失败（数据不足或内部错误）多少只
- 路径层：交集/并集/序列结果是多少，每步过滤的数字
- 报告层：最终命中 N 只，有无解释骨架缺失
- 以上展示在主操盘台结果区（折叠区），而不是独立页面
- explanation_builder 补充"整轮归零/少量命中"的全局解释骨架

**是否属于第二阶段初期**：是，第一批（契约定义）；第二批（完整实现）。

**是否有偏离操盘动线风险**：低。如果做成结果区内的折叠展开，不偏离；如果独立成"诊断中心"页面，则偏离。

**如何避免偏离**：解释信息必须物理上位于主操盘台结果区，采用折叠展开形式。禁止为此创建独立路由/页面。

---

### G3：来源层语义清晰化与诊断字段保留

**解决什么用户问题**：用户不理解"PRO 5000"在不同模式下的含义；问财返回 45 只时不知道为什么；API 调用是否真的发生了不透明。

**包含哪些能力**：
- PRO 5000 语义拆分：在不同来源模式下分别展示对应含义（"问财最多 5000 条，本次实际返回 N 条"；"全A本地名单截取最多 5000 只"）
- 问财诊断字段保留链路：query 原文、actual_count、api_called、elapsed_s 不在 source_resolver 丢弃，传入运行报告
- 问财 0/45/5000 三种边界情况的分别提示文案（0=查询无结果或服务异常；45=问财返回了45只；5000=可能触发截断）
- 来源层诊断字段在状态区和最终报告中内联展示

**是否属于第二阶段初期**：是，第一批。改动范围主要在 source_resolver 和报告层，代码量有限。

**是否有偏离操盘动线风险**：无。它是现有 UI 区域内的标签和提示文案改善，不新增页面。

**如何避免偏离**：所有来源诊断信息内联展示在来源选择区和运行结果区，不建独立的"来源管理"页面。

---

### G4：问财授权验证与 Bridge 双角色定义

**解决什么用户问题**：不知道问财授权是否真的工作；只能把问财当来源，不能对已有结果做验证。

**包含哪些能力**：
- api_key 传递链路验证（在清洁环境下测试 pywencai.get 的授权机制，确认 key 是否真实被使用还是依赖 session）
- 根据验证结果：修复 key 传递路径，或明确文档说明授权机制依赖 session 且如何维护
- 正式定义 Bridge Capability 两种模式：
  - constrained mode：问财查询在已有股票池内检索（输入 = 现有池，输出 = 子集）
  - second-pass mode：先用技能筛选，再对剩余股票做问财验证/标签
- UI 层面：来源区新增"问财验证模式"选项（不是新页面，是参数选项）
- 问财 Bridge 的实际调用实现（second-pass）列为中后期，初期只定义规格

**是否属于第二阶段初期**：授权验证是第一批；Bridge 规格定义是第一批；Bridge 实现是中后期。

**是否有偏离操盘动线风险**：低（规格定义无风险）；中（实现时需确保不新建操盘流程）。

**如何避免偏离**：Bridge Capability 必须作为主操盘台的一个参数选项存在（类似"执行路径"的选择），不能做成独立的"问财验证工作台"。

---

### G5：数据血缘层定义与取数透明化

**解决什么用户问题**：用户不知道本轮数据从哪里来、是否发生了降级、数据是否是今天的。"K线已够用"到底是真的够用还是凑合。

**包含哪些能力**：
- 定义 Data Provider Adapter 统一接口（baostock / akshare / yfinance / 问财 / 手动导入的统一封装层）
- 定义数据血缘字段：股票 + 数据来源 + 是否新拉 + 是否降级 + 最新数据日期 + 是否用旧缓存 + 可信度标注
- FAST_FULL_SCAN 与完整取数模式的行为差异明确区分，在日志和报告中标注本轮使用了哪种模式
- 写缓存失败静默问题修复（`ohlcv_provider.py:195` 的 `except Exception: pass`）
- 本轮数据覆盖情况在运行结果中内联展示（折叠区）："本轮数据 baostock 342 只 / akshare 兜底 12 只 / 失败 3 只 / 最旧 2026-04-15"

**是否属于第二阶段初期**：Provider Adapter 定义和血缘字段规格是第一批；运行结果展示是第二批；历史数据血缘可浏览（如果要做）是第三批。

**是否有偏离操盘动线风险**：高（如果做成独立数据管理页面）；低（如果只展示在运行结果折叠区）。

**如何避免偏离**：血缘信息只展示在当前运行结果内。禁止建立独立的"数据来源浏览器"或"数据管理中心"。

---

### G6：主操盘台与管理中心分流

**解决什么用户问题**：页面信息密度过高，操盘时被历史报告、帮助文档、缓存管理等诊断管理信息干扰。用户找不到操盘必要的信息，因为它被管理信息稀释了。

**包含哪些能力**：
- 主操盘台内容严格限定（见第三节清单）
- 管理中心入口（单一入口，不是侧边导航栏）承接：历史运行列表、分层缓存清理、系统设置、帮助文档
- 历史运行列表（已在右侧 Tab 初步实现）迁移至管理中心，主操盘台结果 Tab 保留最近 1-3 条
- 提示词库是否留在主操盘台或迁入管理中心，根据使用频率决定
- 页面布局调整：释放当前被帮助折叠区、诊断折叠区占据的主操盘台空间

**是否属于第二阶段初期**：中期。需要先完成 G1-G3 建立透明度层，再整理哪些内容进管理中心。

**是否有偏离操盘动线风险**：高（如果管理中心承接了分析能力）；低（如果严格只做管理）。

**如何避免偏离**：管理中心的功能范围铁律：只有"查看历史、清理缓存、系统设置、阅读帮助"四类。任何分析动作（启动运行、调参、解读结果）只能在主操盘台。管理中心没有"启动运行"入口。

---

### G7：运行管理语义正式化

**解决什么用户问题**：abort 按下不知道什么时候生效；"清缓存"不知道清的是哪一层；历史报告看不出和哪次参数对应；断点续跑没有明确的恢复语义。

**包含哪些能力**：
- abort 语义定义：步骤边界停止（安全，下次可续跑）vs 强中止（不保证状态一致）
- 分层缓存清理：★来源快照、★★K线数据库、★★★技能结果库三层独立清理，用户能选择只清哪一层
- 历史运行与参数强关联：每条历史记录明确关联到当时的来源、技能、路径、参数快照
- 断点续跑规格：在哪个步骤中断后可以续跑，续跑的前提条件是什么（数据层是否仍有效）

**是否属于第二阶段初期**：语义定义是初期；实现是中期。

**是否有偏离操盘动线风险**：中（如果运行管理演化成"项目管理"界面）。

**如何避免偏离**：所有运行管理操作的入口必须在管理中心（不在主操盘台），主操盘台只保留"当前运行"的状态和中止操作。

---

### G8：执行路径统一（图执行器）

**解决什么用户问题**：三条执行路径（顺序/并行/混合）的实际代码逻辑和报告里的表达式（`czsc AND kline MINUS landmine`）不在同一条路上，调试时结果无法追溯，将来扩展新路径时维护成本高。

**包含哪些能力**：
- sequential 和 simple_hybrid 路径改走 expression_runner，与 parallel_and 对齐
- 报告里的 expression_spec 真正驱动执行，不再只是文档性描述
- strategy_graph_builder 的图结构与实际执行逻辑保持同一套表示

**是否属于第二阶段初期**：否，列为中后期。这是最大的架构债，但也是改动风险最高的一项。应该等 G1-G5 建立的透明度层稳定后再动，否则在不透明的状态下改执行引擎，很难验证改后的结果是否正确。

**是否有偏离操盘动线风险**：无（纯后端）。

**如何避免偏离**：N/A。

## 五、建议排序

### 第一批（建立信任基础，用户直接可感知）

| 顺序 | 目标 | 理由 |
|------|------|------|
| 1 | **G1 参数-数据-缓存全链路一致化** | 解决"改参数没用"这个最核心的信任问题；改动范围相对清晰 |
| 2 | **G3 来源层语义清晰化** | 改动范围小，解决用户困惑高密度区（PRO 5000、问财 45 只等）；可与 G1 并行 |
| 3 | **G2 全局解释层（契约定义阶段）** | 先把五层解释的规格定义好，为后续实现打基础 |
| 4 | **G4 问财授权验证（验证阶段）** | 在清洁环境下验证授权，结果决定后续如何修复；不改架构，只验证 |

### 第二批（建立透明度展示，用户能看到血缘）

| 顺序 | 目标 | 理由 |
|------|------|------|
| 5 | **G2 全局解释层（实现阶段）** | 规格定完后落地实现；先做来源层和技能层，再补其余三层 |
| 6 | **G5 数据血缘层定义与取数透明化** | 定义 Provider Adapter 规格，修复写缓存静默失败；展示落在运行结果区 |
| 7 | **G4 Bridge Capability 规格定义** | 在授权验证完成后定义两种模式的规格；暂不实现 second-pass |

### 第三批（页面整理与运行管理）

| 顺序 | 目标 | 理由 |
|------|------|------|
| 8 | **G6 主操盘台与管理中心分流** | 在透明度层稳定后，有足够信息决定什么该留、什么该迁移 |
| 9 | **G7 运行管理语义正式化** | 依赖 G6 的分流结构；abort/续跑语义需要与执行引擎状态机协调 |

### 第四批（架构债偿还）

| 顺序 | 目标 | 理由 |
|------|------|------|
| 10 | **G8 执行路径统一** | 最大架构债，风险最高；等前三批稳定后再动 |
| —   | **G4 Bridge second-pass 实现** | 依赖授权稳定 + Bridge 规格定义 + 执行时序灵活性 |

## 六、本轮对齐结论

**第二阶段的定性**：

第二阶段不是新增功能阶段，也不是修 bug 阶段，而是"建立可信度基础设施"阶段。完成后，用户应该能对每次运行结果说清楚：这个结果是怎么来的、数据是什么状态、参数是否真实生效、为什么是这个数字而不是别的数字。

**关于博物馆风险**：

上面列出的所有 8 个目标都不会天然导致博物馆化。博物馆化不是来自"做了太多"，而是来自"每个功能都开了一个新页面"。只要严格执行"诊断信息展示在运行结果内、管理功能集中在管理中心、主操盘台只保留操盘动线"这三条纪律，第二阶段做完后，系统会更简洁，不是更复杂。

**一句话总目标（沿用 012 宗旨）**：

> 让用户在操盘时，能知道自己在相信什么。

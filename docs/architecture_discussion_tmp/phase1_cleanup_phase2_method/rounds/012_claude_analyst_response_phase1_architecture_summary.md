## 一、总判断

**第一阶段不是失败，也不是稳定完成，而是"可运行骨架 + 关键链路待稳定化"。**

这句话需要两半都讲清楚，缺一半都会误导后续决策。

先讲前半句：第一阶段确实建立了一个可运行的系统。它有完整的单页操盘台、六个接通的分析技能、三种可选的执行路径、一套可读的报告体系，以及一个认真设计的两阶段数据隔离理念。这套骨架从 V6 早期的"多页面概念工作台"收敛成了"每天能启动、能看到结果、能调参数"的形态。这是真实的进展。

再讲后半句：这套骨架有几条核心链路还没有稳定下来。它们不是外围功能缺失，而是"参数设了是否真的生效""数据被认为已准备好是否真的准备好""签收报告说通过了是否等于真正通过"这类根本性问题。用户在真实使用时会遇到"系统说够用但其实没准备好""改了参数但结果没变""报告显示的逻辑和实际执行路径不是同一条路"这类体验，这些混乱不是前端文案问题，而是数据链路和执行语义还没有端到端对齐。

所以第一阶段的准确定位是：**骨架立住了，结构跑通了，但结果还不能完全相信**。第二阶段的首要任务不是往上加功能，而是先把已有骨架里的关键链路真正稳定下来，让用户能相信他们看到的结果。

## 二、第一阶段真正做成了什么

对照原始大纲（rescue_charter），以下能力是真实建立的：

**1. 单页操盘台骨架**
从 V6 早期的多页面概念工作台，收敛成了一个有完整用户动线的单页应用：左侧选来源和参数，中间看运行状态，右侧看命中结果。这个形态本身是对的，方向也是对的。UI 里已经有三层数据标记的帮助文字（★ 来源快照 / ★★ K线数据库 / ★★★ 技能结果库），与大纲的用语规范也对齐了。

**2. 六个 live 技能接通**
缠论买点、K线形态、SMC 聪明钱、波浪分析、排雷过滤、问财选股六个技能都有可运行的 producer 代码。排雷的负向语义（命中=应剔除）设计正确，在 skill_registry 里有明确标注。其余 V6 技能资产保留为灰色待接入，没有强行接通防止范围膨胀，这个取舍是对的。

**3. 三种执行路径结构在位**
顺序漏斗、并行取交集、简单混合三种路径都有可运行的代码分支（`execution_engine.py`）。strategy_graph_builder 也能生成可检查的执行计划结构，为后续统一图执行器打下了基础。

**4. 两阶段数据隔离理念**
"网络取数阶段 / 纯本地分析阶段"的设计理念在代码里是落地的：所有 producer 在运行时都设置了 `READ_CACHE_ONLY=true`，不在分析阶段碰网络。这是正确的架构决策。

**5. 内容寻址技能结果库**
`mask_cache.py` 已完整实现：指纹由 skill_id + 排序后的 codes + params + data_date + algo_version 构成，`cache_get` / `cache_put` 都在位。这是第一阶段里设计最认真的组件之一，V6OP-019 的"未实现"判断是过期的，V6OP-026 的"已实现"判断是正确的。

**6. 来源层三种来源结构**
手动输入、全A股、问财选股三种来源都有对应的代码路径，source_resolver 做了统一封装。`PRO 5000` 的档位机制也在位（虽然语义解释还需要对用户说清楚）。

**7. 报告体系基础**
execution_result.json / run_report.json / run_report.md 三层报告结构在位，运行 ID 归档机制（output/runs/<run_id>）在位。explanation_builder.py 已有每只命中股票的中文理由骨架。

## 三、第一阶段没有站稳的地方

以下问题不是散点 bug，而是几条关键链路还没有端到端对齐：

**1. 参数-数据-缓存链路还没有贯通**

系统设计上，用户在 UI 设置的技能参数（如 days）应该沿着"参数 → 取数 → 分析 → 缓存指纹"这条路走到底。但当前这条路有断点：`czsc_producer` 接收了用户设置的 days 参数，但没有把它传给实际读取 K 线的函数（硬编码了 365）；`fetch_planner` 支持 `lookback_days` 参数，但 execution_engine 调用它时没有传入用户的真实 days 设置。结果是：用户以为改了参数，系统内部仍然用默认值计算，但 mask_cache 指纹因为看到了不同的 days 而认为这是新一次计算，放弃了可能有效的缓存。

这不只是 czsc 一个技能的问题，而是参数影响 K线读取的这条关键路径还没有稳定下来。（代码证据：`czsc_producer.py:199`，`execution_engine.py:359,449`）

**2. 问财授权机制不透明**

当前代码里，`IWENCAI_API_KEY` 确实被读取了，但没有传入 `pywencai.get()` 的调用体。这意味着授权实际上是通过什么机制完成的目前不明确——可能是 pywencai 自己维护的 session/cookie 持久化，可能是其他机制，也可能在清洁环境下根本无法成功授权。V6OP-026 记录了一次成功的问财运行（run_20260505_200356，final_hit=3），但这次成功不能证明 key 参数被正确使用了。需要在清洁环境下（无已有 session/cookie）验证：只靠 .env 里的 key，问财是否能成功取数。在这个验证完成之前，这条链路处于"不透明"状态。（代码证据：`wencai_source.py:147-152`，Codex 010 修正口径）

**3. 三路径与报告表达式存在双轨**

原始大纲要求三路径的最终结果与报告表达式一致。当前代码里，`parallel_and` 走了 expression_runner，但 `sequential` 和 `simple_hybrid` 用的是手写集合操作（`pre_exclude_codes` 集合运算）。这两种路径的结果在正常情况下大概率是一致的，但它们不是同一条代码路径，报告里的 `expression_spec`（如 `czsc AND kline MINUS landmine`）是文档性的描述，不是驱动执行的代码。这是第一阶段留下的架构债，不影响当前功能跑通，但影响将来维护和调试时的可信度。（代码证据：`execution_engine.py:780-811`，`strategy_graph_builder.py:149` 注释）

**4. 数据取数主路径与三源降级口径有缺口**

原始大纲描述了 baostock → akshare → yfinance → 旧K线 的四级降级链路。这条链路在 `ohlcv_provider.py` 的标准模式下确实存在。但预取阶段（data_prefetch 的 worker 线程）强制启用了 `FAST_FULL_SCAN` 模式，该模式下 baostock 失败就直接返回 None，没有 akshare/yfinance 兜底。V6OP-026 的 300 只预热 smoke 测试是在全部 cache_hit 的情况下跑的（new_fetch=0），实际上没有测到 baostock 失败时的降级路径。（代码证据：`ohlcv_provider.py:342-356`，`data_prefetch.py:91`）

**5. 运行诊断信息不够完整**

当来源为空、K线不足、技能过严、路径交集过严时，系统目前不能给用户一个完整的"为什么结果是 0"的解释链。问财返回的诊断字段（`query_hash`、`api_called`、`elapsed_s`）在 `source_resolver` 层被丢弃，没有进入报告。这让排查问题变得非常困难，也是用户混乱的根源之一。

## 四、为什么历史签收不能直接等于真实完成

V6OP-026 不是假报告，它记录了当时验收口径下的通过状态，也明确注记了 browser_unavailable、JSON 轮询非 SSE 等限制。这些都是诚实的标注。

但 V6OP-026 的"15/15 全部关闭"用的是局部验收口径，主要依赖以下几类证据：pytest 测试通过数、前端语法检查通过、以及一次可观察到命中结果的真实运行。这些证据能说明"系统能跑通、测试没有基础错误"，但不能说明以下几件事：

- **参数是否端到端有效**：pytest 测试不能验证"用户设 days=730，czsc 是否真的用了 730 天K线"这类参数端到端问题。
- **授权机制是否可靠**：一次成功的问财运行，不能证明 key 参数被正确使用，也不能证明在清洁环境下仍然可用。
- **降级路径是否生效**：300 只预热全部 cache_hit，意味着预热降级路径实际上没有被测到。
- **真实浏览器行为**：Playwright browser_unavailable 已明确注记，这意味着 UI 层没有经过真实浏览器验收。

所以正确的表述是：**V6OP-026 应重新解释为"按当时局部验收口径通过"，其中若干条需要在代码审计后重开、降级为部分关闭、或标记为待验证**。这不是否定签收报告，而是给它加上合理的边界注记，避免把"当时跑通了"直接等于"现在可以在真实使用中相信"。

## 五、原始大纲需要重新解释的地方

**1. 单页操盘台的边界**

大纲强调单页体验，这个方向没错。但"单页"不等于把所有内容都压进一个页面、一个视野、一个 JS 文件。当前页面承载了太多内容——来源、参数、日志、数据标记、结果、帮助文字、历史管理入口……用户在操盘时只需要前半部分，后半部分（管理中心功能、完整帮助、历史报告、缓存清理）应该进入一个独立的管理区，不应该和主操盘动线混在一起。大纲说的"单页"指的是"主操盘动线不需要跳页"，不是"所有功能都在一个屏幕里"。

**2. 问财的定位**

大纲把问财放在"来源层"，这从技术上是对的——问财的主要作用是生成本轮股票池。但用户使用时，问财承担的角色往往不只是"拉个名单"，它的自然语言筛选能力让它同时具备"股票特征描述"的功能。这意味着在某些使用场景下，用户可能希望把问财语句和后续技能配合起来，而不只是用它来拉一个初始池。这个定位不需要马上改代码，但大纲里应该把"问财作为来源"和"问财作为特征筛选器"这两种使用方式分开描述，避免用户不知道在什么情况下该用哪种方式。

**3. 三路径的完成状态**

大纲描述三路径时，隐含了"路径执行和报告表达式是同一套逻辑"的假设。当前代码里，三路径已经可以跑通，但 sequential/hybrid 和 expression_runner 还不在同一路径上。大纲里的"三路径完成"应该加注：当前是"结构可运行"，真正意义上的"路径、报告、表达式三者一致"是第二阶段图执行器统一后才能宣布关闭的目标。

**4. 三源降级的适用范围**

大纲要求 baostock → akshare → yfinance → 旧K线 的四级降级。这条链路在标准模式下已经实现，但大纲没有明确区分"完整取数模式"和"快速扫描模式"的降级深度不同。这个区分需要补充进去：快速扫描（FAST_FULL_SCAN）的设计取舍（只用 baostock，失败不降级）需要在大纲或代码注释中明确说明，并在报告里标注风险，而不是悄悄绕过。

**5. `PRO 5000` 的语义**

大纲没有专门处理档位命名，但 `PRO 5000` 在问财模式和全A模式下含义完全不同。问财模式下是"最多取 5000 条结果"，不保证返回 5000；全A模式下是"从本地A股名单取最多 5000 只"。这两个概念不是一回事，用一个标签覆盖两种语义，是用户混乱的来源之一。大纲需要补充档位命名在不同来源下的语义说明。

**6. 参数可调的保证**

大纲的验收条目之一是"主要技能参数可在 UI 设置"。这条从 UI 层看是完成的，参数面板都在。但大纲隐含的保证是"参数设了会真的影响结果"。当前 czsc 的 days 参数、fetch_planner 的 lookback_days 等链路还没有端到端一致，意味着这条保证还没有完全兑现。大纲应该把验收条目从"参数在 UI 可设置"细化到"参数设置后端到端影响实际计算"。

## 六、用户现在为什么会混乱

用户混乱不是因为功能太少，而是因为系统在几个关键点上给出了"看起来可信但实际不确定"的信息。

**来源层的混乱**：用户不知道问财返回了多少只、为什么是这个数字、问财接口是否真的用了他的 key。系统里有这些诊断信息（query_hash、actual_count、api_called），但它们被 source_resolver 在传递过程中丢掉了，没有进入报告，用户看不到。

**K线层的混乱**：系统告诉用户"K线已够用"，但这个判断是基于检查 `{code}_365d.pkl` 是否存在，不管用户设的是什么 days。用户设 730 天，系统检查 365 天的文件，"够用"了，但实际上 730 天的文件根本不存在或根本没有取。

**"本地保存"概念的混乱**：用户听到"缓存"这个词，不知道说的是问财返回的股票名单、还是本机存的K线数据、还是上次技能算出的结果。这三种东西性质完全不同：第一种下次启动就会被覆盖，第二种只要不清理就持续有效，第三种取决于参数是否变化。当前页面上虽然有三层数据标记的帮助文字，但帮助是折叠的、被动的，用户需要主动去找；而运行状态区的标注还不够直接。

**参数层的混乱**：用户改了参数，系统运行，结果有时没变。他不知道是因为技能本来就不会命中、还是因为他的参数没有真正影响计算。在 czsc 的 days 链路没有修复之前，这个怀疑是合理的。

**结果解释的混乱**：当命中数为 0 时，用户不知道是来源返回了 0、K线不足、技能过严、还是并行交集太严。当前报告里没有一个"为什么是 0"的完整解释链，explanation_builder 已有每只命中股票的解释骨架，但"整轮为什么没有命中"这个全局解释层还缺失。

**页面信息密度的混乱**：主操盘页面上，重要的操作信息（来源、参数、结果）和诊断信息（数据标记、取数记录、日志、帮助文字）混在同一个视野里。用户在操盘时不需要看这么多，但需要的信息又不够突出。

## 七、第二阶段开发宗旨

**先让结果可信、路径可解释、参数真实生效，再谈扩展能力。**

这一句话是第二阶段的优先级排序原则，不是限制扩展，而是说扩展要建立在可信基础上。

更具体地说，第二阶段的宗旨是：

**让用户在操盘时，能知道自己在相信什么。**

这意味着：当系统说"K线已够用"时，K线真的是按用户设置的 days 准备好的；当用户改了参数时，结果确实基于新参数计算；当问财返回 45 只时，报告能说清楚为什么是 45 不是 80；当命中数为 0 时，报告能告诉用户是哪一层把结果变成了 0，以及下一步应该调什么。

在这个基础上，第二阶段才有条件讨论接入新技能、引入打分制、建立管理中心等扩展方向。这些方向不是不重要，而是要等前一阶段的基础稳住之后再谈。

## 八、第二阶段候选改造方向

以下是方向级别的描述，不是施工命令。具体实施方式和优先级需要在正式第二阶段讨论中决定。

**方向一：参数-数据-缓存链路端到端一致化**
让用户设置的 days 参数真正沿着"参数 → K线取数 → 分析 → 缓存指纹"这条路走到底，每一个环节都使用相同的 days 值。这是让"参数真实生效"的前提。

**方向二：问财授权机制明确化**
在清洁环境下验证问财授权的真实路径。根据验证结果，要么修复 key 传递路径，要么明确文档和 UI 说明问财依赖的是其他授权机制（session/cookie）及其维护方式。

**方向三：全局解释层**
在现有的 explanation_builder（每只股票的命中理由）基础上，增加一个"整轮为什么是这个结果"的全局解释层：本轮来源从哪里来、有多少只、K线准备了多少只、每个技能命中多少失败多少、路径合并后剩多少、最终结果是多少。这个解释层不只属于报告，也应该出现在运行状态区域。

**方向四：取数路径透明化**
明确区分"完整取数模式（三源降级）"和"快速扫描模式（仅 baostock）"的适用场景，在报告和日志中标注本轮用的是哪种模式、是否发生了降级或失败。让用户能区分"baostock 失败但 akshare 兜住了"和"baostock 失败直接没数据"。

**方向五：执行路径与报告表达式统一**
逐步推进三路径的统一图执行器，让 sequential/hybrid 也走 expression_runner，使报告里的表达式（`czsc AND kline MINUS landmine`）真正对应实际执行逻辑。这是 V6OP-026 已明确列为 Phase 2 的任务。

**方向六：来源诊断信息保留与展示**
在 source_resolver 和 run_report 层保留问财的诊断字段（query 原文、actual_count、api_called、elapsed_s 等），让用户在命中数异常时能追溯到来源层。

**方向七：页面信息分流**
将主操盘页面承载的内容按"操盘动线需要"和"管理/诊断需要"两类分流。操盘动线保留：来源、参数、路径、启动、状态、结果、本轮解释。诊断和管理功能（历史报告、清缓存、续跑、完整帮助、技能资产说明）移入独立的管理中心。这不是重写页面，而是做内容的优先级排序和分流。

**方向八：运行管理能力补全**
当前 abort、清缓存、历史报告、断点续跑这些功能大多只有前端按钮或简单实现。第二阶段需要给它们真正的后端语义：abort 是步骤边界停止还是强中止？清缓存清的是哪一层？历史报告如何关联到对应的股票池和参数？这些问题在第二阶段需要设计，不能直接做前端。
